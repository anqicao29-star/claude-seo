## 大白话总结

以前用户点击“发送”以后，只能等 Codex 自己结束。网页上的“新对话”虽然能刷新页面，但不等于真正停止后台任务，Codex 或它启动的子进程仍有可能继续运行。

这次给每个任务增加了自己的“任务编号”和生命周期：

- 任务刚建立时是“正在启动”。
- Codex 开始工作后是“运行中”。
- 用户点击取消后是“请求取消”。
- 最后只能进入“完成、失败、已取消”三种结果之一。

网页现在有真正的“取消任务”按钮。点击后不是简单隐藏页面，而是向后台发送取消请求，后台找到对应的 Runtime 会话并停止它。

简单说，这次把“关掉页面上的进度提示”升级成了“真的让后台停下来”。

## 本次完成内容

1. 建立线程安全的内存任务状态机。
2. 每次聊天分配独立的应用任务 ID，例如：
   - `task_0123456789abcdef...`
3. 任务 ID 同时通过以下方式返回：
   - HTTP `X-Task-ID` 响应头。
   - NDJSON 流中的首个 `task` 事件。
4. 增加取消接口：
   - `POST /api/tasks/{task_id}/cancel`
5. 取消请求会调用对应 Runtime 会话的 `terminate()`。
6. 支持“用户在 Runtime 尚未完全启动前就点击取消”的竞态情况。
7. 不存在的任务返回 `task.not_found`。
8. 已经结束的任务返回 `task.not_cancellable`。
9. 任务记录达到上限时返回可重试的 `task.capacity_exceeded`。
10. 前端增加“取消任务”按钮和“任务已取消”结果提示。

## 当前限制

- 任务状态目前保存在内存中，软件完全退出后不会保留。
- 应用重启后的任务恢复属于 05 封闭测试加固阶段。
- 当前还没有任务超时和并发任务数量限制。
- 前端仍然保存 Codex 的 `thread_id`，还没有完全改为应用自己的会话 ID。
- 取消真实 Codex 长任务还需要在后续桌面环境中进行端到端测试。
