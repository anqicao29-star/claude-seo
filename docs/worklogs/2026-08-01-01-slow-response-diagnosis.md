# 工作日志：诊断工作台为什么一直很慢

- 日期：2026-08-01
- 阶段：轻量可交付版本
- 工作类型：只读诊断
- 状态：已找到原因，没有修改或停止进程

## 大白话总结

这次慢不是 Codex 或 Claude 正在生成内容，而是之前启动的 Claude 登录进程一直没有结束。

该登录进程已经持续约 3 天 20 小时。后台看到它仍然存在，就认为“Claude 还在登录中”。用户再次点击登录按钮时，后台不会新开一次登录，而是继续等待这个已经失效的旧流程，所以页面长时间显示等待状态。

## 本次检查结果

1. 本地工作台正在正常运行。
2. `/api/runtime` 返回 HTTP 200，响应时间约 0.39 秒。
3. Codex 已登录。
4. Claude 仍未登录。
5. 当前没有 `codex exec` 或 `claude --print` 写作任务运行。
6. 存在一个持续约 3 天 20 小时的 `claude auth login --claudeai` 进程。
7. 后台日志里有大量重复的登录状态查询，说明网页此前一直轮询登录结果。

## 为什么再次点击也没用

当前登录启动器为了防止重复打开多个认证窗口，只要发现旧登录进程还活着，就会返回“已有登录正在运行”。

这个防重复设计本身合理，但缺少超时回收：即使官方登录页面早已过期，只要 CLI 进程没有自动退出，工作台就永远不能发起一轮新的登录。

## 建议修复

1. 为 Claude 登录进程增加 5 到 10 分钟超时。
2. 超时后自动结束失效登录进程。
3. 用户重新点击登录时，先检查旧流程是否超过有效时间。
4. 如果已经过期，清理旧流程并重新打开官方登录页面。
5. 页面明确显示“登录已过期，请重新登录”，不要一直显示“等待登录”。
6. 可选优化：短时间缓存 Runtime 状态，减少重复启动 CLI 检查造成的等待。

## 本次为什么没有直接结束进程

用户这次问的是“为什么这么慢”，属于原因诊断。结束进程和修改登录逻辑会改变当前运行状态，因此本次先报告原因，没有擅自操作。

## 距离封闭测试还有多久

- 这个问题是明确、局部的登录状态管理缺陷。
- 修复并验证预计需要半天以内。
- 修复后仍需在不同电脑验证首次登录和文章输出，小范围封测预计还需要 3–7 天。
